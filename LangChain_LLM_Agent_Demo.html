Presentation — explain the architecture in 5 steps

First, the user submits a support question or ticket to the application.

For predictable workflows, the application uses a chain, where the execution order is defined by the developer.

For policy questions, the application uses RAG to retrieve relevant support documents before calling the LLM.

For requests that require an action, an agent can dynamically choose a lookup or calculation tool.

The LLM then uses the retrieved context or tool result to produce the final response.

I built a LangChain-based customer support copilot prototype as a hands-on project for learning modern LLM application architecture.

I started with prompts and structured output using Pydantic, then added conversation memory and deterministic chains.

🧾 Structured Output & MemoryFROM FREE TEXT TO A SCHEMA 01›

LLMs naturally return free-form text, but applications often need predictable fields such as category, priority, product, or summary.

A structured schema gives downstream code a stable contract instead of parsing arbitrary natural language.

In this project, structured output is part of the support-ticket workflow and is demonstrated with Pydantic-style validation.

Conversation Memory

Without memory, every LLM call is effectively independent unless previous messages are supplied again.

Conversation memory keeps relevant prior context so follow-up questions can refer to earlier information.

The key design question is not simply whether to store everything, but what context is useful, how long to keep it, and how to control token growth.

Memory Point: Memory = conversation state. RAG = external knowledge. They solve different problems.

The developer controls the sequence; the LLM performs tasks inside that sequence.

Retrieve relevant policy text first, then send that context to the model.

RAG stands for Retrieval-Augmented Generation: retrieve relevant external knowledge first, then provide it as context to the model.

In this project, the knowledge source is local support-policy documents, and FAISS is used as a lightweight vector index.

The goal is to make answers more grounded in source documents instead of relying only on the model's parametric knowledge.

🧪 Evaluation StrategyFROM 'LOOKS GOOD' TO REPEATABLE TESTS 05›

LLM output is probabilistic, so manually reading one answer is not enough to judge a change reliably.

This project includes repeatable evaluation cases that compare generated behavior against expected cases.

For a larger production system, I would separate retrieval evaluation from answer-generation evaluation.

🔢 RAG FundamentalsWHY SEMANTIC RETRIEVAL WORKS 01›

An embedding converts text into a numerical vector that represents semantic meaning.

Documents with similar meaning tend to have vectors that are close in the embedding space.

FAISS performs efficient similarity search over these vectors and is convenient for a local prototype because it does not require an external vector database service.

Key RAG Q&A
QWhy RAG instead of fine-tuning?
PointDynamic knowledge.
A

The policy data can change. RAG lets me update documents and the retrieval index without retraining the model.

QWhy FAISS?
PointLightweight prototype.
A

FAISS is a lightweight local vector index for similarity search, so it is convenient for a prototype without external vector-database infrastructure.

QWhat can go wrong in RAG?
PointRetrieval and generation can both fail.
A

The retriever may return irrelevant or incomplete context, or the model may ignore or misinterpret good context. I would evaluate these layers separately.

QHow do you reduce hallucination?
PointGrounding, constraints and evaluation.
A

I retrieve relevant evidence, instruct the model to answer from that context, expose sources where possible, and evaluate faithfulness on representative cases.

The model requests a tool call; the application executes the Python function.

An agent adds dynamic decision-making: the model decides whether a tool is needed and which available tool fits the request.

In this demo, the agent routes requests across lookup and calculation tools.

The agent should not be viewed as magical autonomy; it is still constrained by the tools, prompts, state, permissions, and execution loop defined by the application.

Tool Calling Flow

1. Model decision

Read user request
Choose tool name
Generate structured arguments
→

2. Application execution

Validate tool request
Execute Python / API / retrieval function
Capture result or error
→

3. Final generation

Return tool result to model
Generate user-facing answer

The LLM does not directly execute the function. It produces a structured tool request, and the application executes the tool.

This separation matters because the application remains responsible for validation, permissions, error handling, and side effects.

User: "What is the refund amount after a 15% fee?" LLM → tool_call: { "name": "calculate_refund", "arguments": { "amount": 100, "fee_rate": 0.15 } } Application → execute calculate_refund(...) Tool result → 85 LLM → "The refund amount is 85."

Key Agent Q&A
QWhat is an LLM agent?
PointDynamic action selection.
A

An LLM agent is an application pattern where the model can decide the next action, often by selecting tools, observing results, and continuing until it can produce a final answer.

QWhat is tool calling?
PointStructured request, application execution.
A

The model generates a structured request describing the tool and arguments. The application validates and executes the actual function, then returns the result to the model.

QWhy not use an agent for everything?
PointAgents add flexibility but also uncertainty.
A

For predictable workflows I prefer chains because they are easier to control, test and bound. I use agents when runtime action selection provides real value.

QWhat are the main agent risks?
PointWrong tool, wrong args, loops and side effects.
A

The model may choose the wrong tool, generate invalid arguments, repeat unnecessary steps, or trigger unwanted side effects. Production systems need validation and permission boundaries.

QHow is an agent different from RAG?
PointCapability vs knowledge.
A

RAG retrieves knowledge. An agent decides actions. A RAG retriever can itself be exposed as one of the tools available to an agent.

QHow would you productionize this demo?
PointAPI, state, security, observability and evaluation.
A

I would add an API layer, persistent state, authentication, tool permissions, tracing, retry and timeout policies, offline evaluation, monitoring, and deployment automation.

QWhy LangChain?
PointReusable orchestration abstractions.
A

It provides reusable interfaces for models, prompts, retrievers, structured output, tools and agent workflows, which makes it easier to compose an LLM application without writing every orchestration component from scratch.

QWhat did you personally learn from this project?
PointArchitecture, not just API usage.
A

The main learning was how the components fit together: structured contracts for outputs, state for conversation, retrieval for external knowledge, evaluation for reliability, and tools for actions.

Agent Summary

The final part of the project was a tool-calling agent. Instead of following a fixed workflow, the model can inspect the user request and decide which available tool to use.

The demo exposes lookup and calculation capabilities, and the model produces a structured tool request with the selected tool and arguments.

The application executes the tool and returns the result to the model, which then generates the final response.

The important design point is that the application controls the tools and execution boundary; the model only decides from the options it is given.
